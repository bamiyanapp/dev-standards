# フェーズ5: 品質課題の棚卸しとリファクタリング

[`ai-driven-app-curriculum.md`](ai-driven-app-curriculum.md)のフェーズ5の詳細である。

フェーズ4の観点は、lint・カバレッジ等の機械的な基準である。これらを満たしても、プロダクト固有の課題は残る。例えば、認証なしAPIの濫用による課金、DynamoDBのページング漏れによるデータ欠落、エラー時に画面へ何も表示されない挙動等である。本フェーズでは、こうした外部品質（セキュリティ・性能・信頼性・使いやすさ）と内部品質（保守性・テスト容易性）の課題を棚卸しし、issueにして改善する。

## モデルの使い分け

課題の洗い出しと設計判断は、上位モデル（Fable等）に任せる。実装は安価なモデルで進める。

安価なモデルは、指示が明確なら実装は十分にこなせる。一方、設計判断（方式の比較、展開順序、iOS Safari等の環境固有の制約への配慮）を任せると誤りやすい。そこで、上位モデルに設計判断までをissue本文へ書き込ませる。安価なモデルはそれに従って実装するだけで済む状態にする。

Claude Code on the webでは、`/model`コマンドでセッションのモデルを切り替えられる。

## 進め方

1. 上位モデルへ切り替え、後述のプロンプトで課題の棚卸しを依頼する
2. 起票されたissueを確認する。ユーザーの判断が必要な点（例: 検索エンジンへのインデックスの可否）があれば回答する
3. 安価なモデルへ切り替え、issueを1件ずつ実装させる。issueに記載された着手順序の依存に従う
4. 実装中に、issueに書かれていない設計判断が必要になった場合を考える。安価なモデルに判断させず、issueへコメントさせて止める。その判断だけ上位モデルで行う

大きな機能追加の後など、プロダクトが一段育った区切りで繰り返し実施する。

Lambda + API Gateway + DynamoDB構成のプロダクトでは、複数のプロダクトで繰り返し見つかった項目を[`serverless-api-hardening-checklist.md`](serverless-api-hardening-checklist.md)にまとめている。棚卸しの依頼時に、このチェックリストとの照合もあわせて指示する。

## プロンプトの例

```
プロダクト側の外部品質、内部品質の課題を挙げ、イシューにして
各イシューについて、安価なモデルで開発を進めるが、上位モデルでないと
設計が難しい点があればイシューを詳細化し、追加して

次の3点を守ること。
- 冒頭で現在のモデルを確認し、上位モデルでなければ、起票せずに止まって知らせる
- 重要度は、実際のデータ量・利用者数・設定値を確認してから付ける。確認できなければ、その旨をissueに書く
- 起票の前に、開発共通側の既存issue・serverless-api-hardening-checklist.md・shared/と照合する。共通部品で解決できるものは、開発共通側へ起票するか既存issueへ追記し、プロダクト側のissueから参照する
```

このプロンプトの要点は、設計判断を要するissueに「設計（確定事項）」の節を書かせることである。判断の内容だけでなく理由も書かせる。理由が無いと、安価なモデルが実装中に「より良さそうな別案」へ勝手に変えてしまうためである。複数issueの着手順序の依存も明記させる。

## 設計の確度が低い箇所を、後から見直せるように残す

毎回上位モデルで棚卸しすると、コストがかさむ。安価なモデルで実行したときは、実行を止めない。代わりに、設計の確度が低い箇所を機械的に探せる形で明示する。複数のプロダクトぶんの棚卸しが溜まった段階で、上位モデルがまとめて見直す。

### マーカーを付ける

設計判断を伴うセクション（「設計検討」「設計上の要点」等）の末尾に、書いたモデルとeffortを示す定型の文を付ける。

```
⚠️ 設計レビュー状況: 本セクションは<モデルID>（effort: <low・medium・high等>）が記載した。
上位モデルによる設計レビュー未実施。
```

### マーカーを更新する

- 上位モデルが見直して設計を確定したら、マーカーを「設計レビュー済み」へ改める。モデルIDと日付を添える。
- 開発共通側との照合で、既存の共有部品やチェックリストで解決できると分かったら、同じIssueへ追記する。マーカーは「解決済み（参照: dev-standards#NNNN）」へ改める。
- 実例は、uchi-stock/youtube-radar#199〜#208である。

### 見直しの進め方

本文に「設計レビュー状況」を含むIssueを横断して一覧にする。上位モデルが、まとめて見直す。

次の3点は、まだ決めていない。運用しながら決める。

- マーカーの検索を、キーワード一致だけに頼るか。ラベル（例: `needs-senior-review`）を併用するか。
- 横断レビューを、定期実行のSkill（pr-sweepのようなもの）にするか。利用者が任意のタイミングで依頼するか。
- 複数プロダクトから集まったIssueの優先順位を、重要度順にするか。プロダクト横断で共通するパターンの発見を優先するか。

## 失敗パターンと対処

- **安価なモデルで棚卸しが実行された**: 「設計が必要」とだけ書かれ、設計の中身が無いissueが並ぶ。見落としも多い（重要度の高い課題を含む）。モデルを確認してやり直す。起票済みのissueは捨てず、上位モデルに見直させる（重要度の修正と設計の追記）
- **コードの形だけで重要度を付けた**: 全件`Scan`を「データ欠落の恐れ」で`priority: high`にしたが、実データは147件・約29KBで上限に遠かった。実データ量を確認してから付ける
- **開発共通側との照合が無い**: 共通部品のissueが既にあるのに、プロダクト側で同じ部品を設計してしまう。起票前に照合する

## 設計を確定できないissueの扱い

利用者にしか決められない点（誰が使う想定か、等）が残るissueがある。次のように書く。

- 選択肢と、それぞれの長所・短所を書く
- 推奨案を1つ示す
- 「着手前に決めてほしい」と明記する。決まるまで、安価なモデルに着手させない

## 実例

- karuta#2178〜#2192（15件、うち設計を確定させたもの6件）
- Camp-Stock#563〜#581（19件、うち設計を確定させたもの16件、利用者の判断待ち1件）。文書のプロンプト例どおりに実行して、上記の失敗パターンが3つ起きた
