# ログイン無しの公開書き込みAPIの不正データ対策

## 目的

ログインの無い、公開の書き込みAPIを持つアプリがある。例は、ランキングへの記録の投稿や、匿名で意見を集める機能である。
このAPIは、誰でも`curl`で直接呼べる。**不正な投稿を、完全に防ぐことはできない。**
目的は、被害を、許容できる範囲に抑えることである。対策は、効果とコストで選ぶ（[#1456](https://github.com/bamiyanapp/dev-standards/issues/1456)）。

## 結論

| 防御 | 防げるもの | コスト | 方針 |
|---|---|---|---|
| 1. 妥当性範囲チェック | 非現実的な値 | 小 | 必須 |
| 2. 送信元IP単位の回数上限 | 大量の投稿・費用の増加 | 小〜中 | 通常は採用する |
| 3. CORSの限定 | ブラウザ経由の悪用 | 小 | 採用する。直接呼び出しには効かない |
| 4. 署名（ビルド埋め込みの共有シークレット） | 素人の直接投稿 | 中 | 原則、採用しない |
| 5. 使用量プラン・WAF | 全体の流量 | 設定または固定費 | 原則、採用しない |

## 1. 妥当性範囲チェック（第一の防御線）

アプリのドメイン知識から、値の上限と下限を導く。範囲を外れた投稿は、拒否する。
例えば、制限時間30秒のゲームで、捕獲数が1000という記録は、あり得ない。

- `shared/lambda/validation.js`の`requireNumber(value, field, { min, max, integer })`を使う。数値の文字列・`NaN`・無限大は、拒否される
- 失敗時は、`statusCode: 400`の例外になる。エラー文言に、入力値は含まれない
- 範囲の根拠は、コードのコメントに残す。後で、根拠を確かめられるようにする

**範囲内の不正な値は、防げない。** 高得点を、範囲内の値で偽る投稿は、通る。この限界は、割り切る。

## 2. 送信元IP単位の回数上限

1つのIPから、1日に投稿できる回数を、制限する。実装は、[`daily-rate-limit-pattern.md`](daily-rate-limit-pattern.md)にある。
学校やイベント会場では、多数の端末が、同じIPを共有する。上限は、通常の利用で届かない値に、余裕を持って決める。

## 3. CORS

許可オリジンを、自サイトのドメインに限定する（[`serverless-api-hardening-checklist.md`](serverless-api-hardening-checklist.md)）。
ブラウザ経由で、他のサイトから悪用されることを、防げる。
**`curl`等の、ブラウザ以外からの呼び出しには、効かない。** `Origin`ヘッダーは、自由に偽装できるためである。

## 4. 署名を、原則、採用しない理由

「このリクエストは、本当に、このフロントエンドから来たか」を、署名で確かめたくなる。ビルドに埋め込んだ共有シークレットで、HMAC署名を付ける方法である。
しかし、シークレットは、フロントエンドのバンドルに入る。ブラウザの開発者ツールで、誰でも取り出せる。取り出せない人にしか、効かない。

- ログインの無い前提を崩さずに、「本物のフロントエンド」を保証する方法は、無い
- シークレットの更新は、ビルドのたびになる。誤って、正当な利用者を拒否するリスクもある
- 効果に比べて、実装と運用のコストが大きい

## 5. 使用量プラン・WAF

API Gatewayの使用量プランは、APIキーを前提にする。キーも、フロントエンドへ埋め込むため、認証にはならない。流量を抑える用途である。
WAFは、月額の固定費が発生する。どちらも、全体の流量は抑えられる。しかし、1日の総量（例えば、通知の送信数）は抑えられない。1日の総量は、2の回数上限で抑える。

## 6. 小規模な利用での、バランスの取り方

[`standard-tech-stack.md`](standard-tech-stack.md)は、身内中心の小規模な利用を想定している。対策は、被害に見合った大きさにする。

- 最初は、1・2・3だけにする。4・5は、被害が出てから、検討する
- 強化の判断は、「荒らされたときの被害が、対策のコストを上回ったか」で決める
- **不正なデータを、運用で消せるようにしておく。** 防ぎきれない前提で、後から、取り除く手段を用意する。例えば、管理用のスクリプトで、範囲外の記録を、検索して削除する

## 実例

- `uchi-stock/kingyo`: ランキングの投稿API（`POST /ranking`）。この文書の元になった（kingyo#167）
- `karuta`: 入力検証は、実装済み。1日あたりの回数上限は、設計済みである
