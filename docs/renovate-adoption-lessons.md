# Renovate導入初期の脆弱性と対処方針

Renovateを新規導入した直後のリポジトリでは、しばらくの間CIが依存更新PRで頻繁に失敗する時期が発生しやすい。本ドキュメントは、karutaリポジトリでのRenovate導入（issue #285、2026-07-05）直後の約1〜2ヶ月間に実際に発生した事象を事例として整理する。そのうえで、他の参照側リポジトリが同じ時期を通過する際の対処方針を共通知見としてまとめる。

## なぜ導入直後に集中して問題が起きるのか

Renovate導入前のリポジトリは、依存パッケージの更新が長期間放置された状態（各パッケージが異なるタイミングで個別に手動更新される、または全く更新されない）になっていることが多い。Renovateを入れると、それまで蓄積していた「本来もっと早く追従すべきだった更新」が短期間に一括して提案される。この一括追従の過程で、以下の3種類の問題が集中して表出する。

1. **関連パッケージ間の足並みの乱れ**: peer dependencyで結びついた複数パッケージ（vite本体とプラグイン、eslint本体と各プラグイン等）がある。これらは、Renovateの既定動作では個別のPRに分かれて提案される。片方だけ更新されると`npm ci`がpeer dependency不整合（ERESOLVE）で失敗する
2. **テストコード側の暗黙の前提の破綻**: テストフレームワーク（vitest等）のメジャー更新で、テストコードが依存していた細かい実装詳細（モック関数の`this`バインディング等）の仕様が変わる。これにより、アプリケーションコードは無傷でもテストだけが落ちる
3. **実行環境・外部サービスの要求とのバージョン不整合**: ランタイム（Node.js等）やCLIツール（Serverless Framework等）のメジャー更新がある。これが、依存関係グラフには表れない制約と衝突する。この制約とは、Lambda等の実行環境の対応バージョンや外部サービスのサインイン要件である

## 実際に発生した事象と対処

### 1. peer dependency不整合によるCI失敗（ERESOLVE）

vite本体とプラグイン（`@vitejs/plugin-react`）が個別PRで提案され、片方のみがマージされるとpeer dependency要求を満たせず`npm ci`が失敗した。eslint本体と周辺プラグイン（`eslint-plugin-react-hooks`等）でも同様の事象が発生した。

**対処**: `renovate.json`の`packageRules`で関連パッケージをグループ化し、単一PRにまとめて提案されるようにした。さらに、グループ化しただけではメジャー更新と非メジャー更新が別PRに分離される既定動作までは止まらず、同じ問題が再発した。そのため`separateMajorMinor: false`を追加し、グループ内の更新種別を問わず単一PRに統合した。

```jsonc
{
  "packageRules": [
    {
      "groupName": "vite",
      "matchPackageNames": ["vite", "@vitejs/plugin-react"],
      "separateMajorMinor": false
    }
  ]
}
```

### 2. テストコードのみがフレームワーク更新で破綻する

テスト側では、`vi.fn().mockImplementation(...)`内でアロー関数を使った`new`呼び出し可能なモック（`window.Audio`・`jsPDF`等のモック）を使用していた。vitest v3→v4更新で、これらのモックが失敗するようになった。これは、JS仕様上元々コンストラクタ不可だったアロー関数の扱いが、v4でより厳格に検証されるようになったためである。これにより「... is not a constructor」エラーになった。

**対処**: テスト側のモック実装をアロー関数から通常の関数式へ修正した。アプリケーションコード自体への影響は無かった。この種の問題は依存更新PRのCI失敗を個別に調査しないと気づけない。そのため、「Renovate PRのCI失敗は依存先のバグではなく自分のテストコードの前提が古い」という可能性を優先して疑う姿勢が有効だった。

### 3. ランタイム・外部サービス要件との不整合

- Serverless Framework v3→v4更新で、CLIバイナリがv4系ではSaaS（app.serverless.com）へのサインインを必須とするようになった。これにより、CI環境でのデプロイが`You must sign in or use a license key...`で失敗した。`frameworkVersion`をv3系の完全バージョン番号（`3.40.0`、メジャーのみの指定`'3'`は解決不可だった）で固定した。さらに、`renovate.json`に`<4.0.0`の`packageRules`を追加して再度の自動更新を防止した
- `puppeteer-core`のメジャー更新が要求する`engines.node`の下限値が、当時のLambdaランタイムのNode.jsバージョンと非互換だった。ランタイム側を先に上げてから制約を緩めるか、制約が解消するまで`renovate.json`側でバージョン上限を固定する運用で対応した
- Node.jsのメジャーバージョンには、Renovateが検知できる参照（`.nvmrc`等）とできない参照（ワークフローの`node_version`入力等）が混在する。この状態で自動更新させると、一部の参照だけが更新される。その結果、CI・CD・実行環境間でバージョンが食い違う状態になった。Node.jsのメジャーバージョン自動更新自体を`renovate.json`で無効化した。メジャー更新時は全参照を手動で揃える運用に切り替えた

**共通の対処方針**: 依存関係グラフだけでは見えない制約（実行環境の対応バージョン、外部サービスのサインイン要件等）がある。これに抵触するパッケージは、個別のバージョン固定ルールを`renovate.json`に追加する。固定した直後にRenovateが同じ更新を再度提案してくる場合がある。そのため、`packageRules`での制約を確実に設定ファイルへ反映する（コミットメッセージに経緯を書くだけでは、Renovateの提案自体は止まらない）。

### 4. Renovate PRのCIがすぐ陳腐化する

mainへのマージ頻度が高いリポジトリでは、Renovate PRのブランチがRenovate作成時点のmainから分岐したまま更新されなかった。そのため、CIの検証結果が実際には無関係な依存関係の組み合わせに基づいた古い状態に固定されていた。これにより、PR自体には問題が無くても、他の変更との組み合わせでlint/testが失敗する状態が繰り返し発生した。

**対処**: `renovate.json`に`rebaseWhen: "behind-base-branch"`を設定し、mainが更新されるたびにRenovateがブランチを自動的に作り直すようにした。これにより、CIが常に最新mainとの組み合わせで実行されるようになった。

```jsonc
{
  "rebaseWhen": "behind-base-branch"
}
```

## 導入時に先回りで検討すべきこと

上記の事象は、Renovate導入前には予測しづらく、実際にCIが落ちてから対処する形になったものが大半である。一方で、以下は導入時点であらかじめ設定しておくことで、同種の問題の発生頻度を下げられる。

- **関連パッケージのグループ化**: vite・eslintのように、本体とプラグインがpeer dependencyで密結合しているエコシステムがある。このようなエコシステムは、導入時点で`packageRules`によるグループ化・`separateMajorMinor: false`を設定しておく
- **`rebaseWhen: "behind-base-branch"`**: mainへのマージ頻度が高いリポジトリでは、導入時点から設定しておく
- **実行環境依存のパッケージの洗い出し**: ランタイムのバージョン（Lambda・Node.js等）、デプロイツールのCLI挙動（Serverless Framework等）に依存するパッケージがある。こうしたパッケージは、メジャー更新を自動マージ対象から外すことを検討する。または`minimumReleaseAge`（karuta issue #1309）でリリース直後のパッケージを一定期間経過するまで提案しない猶予期間を設ける
- **自動マージとの組み合わせに注意する**: 自動マージを有効にしている場合、上記の問題は「CIが落ちたPRがマージ待ちで溜まる」ではなく「問題のある更新がそのままmainへ入る」形で表面化する。経路を体で理解するまでは、少なくともメジャー更新は自動マージ対象外にしておくことも選択肢になる
