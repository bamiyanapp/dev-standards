# 公開リポジトリに個人情報を持ち込まないパターン

**前提**: dev-standardsの標準構成（`docs/standard-tech-stack.md`「2. ログイン」）はフロントエンド自体を誰でも閲覧できる状態に保つ方針であり、bamiyanapp配下のリポジトリも基本的に公開（Public）である。**「フロントエンドが公開」と「リポジトリが公開」は同じ前提の両面**であり、どちらか一方だけを意識しても個人情報は守れない。ソースコード・コミット履歴・PR・Issueを含むリポジトリ全体を「誰でも常に閲覧できるもの」として扱い、実在の個人情報を一切持ち込まない設計にする。

対象読者はプロダクト固有のドメインロジックで実在の個人（家族・顧客・ユーザー）のデータを扱う全プロダクト（examination等）。

## 原則: 個人情報は「実行時にAPIから取得する」以外の形でリポジトリに存在してはならない

- コンテンツファイル（Markdown等）・シードスクリプト・テストフィクスチャ・コード中の文字列リテラル・コードコメントに、実在の氏名・生年月日・住所・電話番号・学校名・園名・勤務先・医療情報等を直接書かない
- 実データが必要な例・プレースホルダーには、汎用的なサンプル値（日本語の「山田太郎」「○○」等、英語圏の"John Doe"相当）のみを使う。実在すると誤認されない一般的な値を選ぶ
- 個人単位で異なる実際の値（家族の氏名等）は、DB（DynamoDB等）へ保存し、認証済みAPI呼び出しで実行時に取得する設計にする（`docs/short-lived-bearer-token-pattern.md`のBearerトークンパターン等）。フロントエンドのビルド成果物（JSバンドル）自体には決して焼き込まない
- 静的サイト生成（MkDocs等）を使う場合も同様に、実際にビルドされるページに個人情報を含めない。個人情報を含む可能性のあるコンテンツソースは、ビルド対象そのものから除外する（`exclude_docs`等）か、そもそもリポジトリに置かず外部の非公開ストレージで管理する

## 原則: 一度コミットした個人情報は「消せない」前提で運用する

GitHubの公開リポジトリでは、個人情報を含むコミットを後から発見しても、完全な削除は事実上不可能に近い。

- `git filter-repo`・BFG等による履歴書き換え＋force pushは、コミットのSHAを変えるだけで、**マージ済みPRの差分ページ（Files changed）はそのまま残る**（GitHubはPRの削除機能自体を提供していない。削除できるのはIssueではなくリポジトリ全体のみ）
- 唯一の完全な削除手段はリポジトリそのものの削除・作り直しであり、Issue・PR・Star・Discussion等すべてを失う大工事になる
- したがって、「後で気づいたら消せばよい」という前提は成り立たない。**コミットする前に気づく**ことが唯一の実効的な対策であり、この文書のチェックリスト・レビュー観点はそのために存在する

## 原則: 個人情報を「消す」コミット・PR自体に実際の値を書かない

過去に混入した個人情報へ後から気づき削除する場合、その修正のコミットメッセージ・PR本文・Issue本文には、**削除対象の実際の値そのものを書いてはならない**。書いた場合、その修正コミット自体が新たな漏洩源になる（しかもコミットメッセージは通常のファイル内容以上に、後から編集する手段が無い）。

- 悪い例: 「実在の志望校名『◯◯小学校』を削除した」（実際の値を明記してしまっている）
- 良い例: 「実在の志望校名（1件）を削除した」（種別・件数のみを記載し、値自体は書かない）

## コミット前チェックリスト

`commit` Skillの前提条件に加え、以下を確認する。

- [ ] ステージ済み差分に、実在の個人情報（氏名・生年月日・住所・電話番号・学校名・園名・勤務先・医療情報等）がハードコードされていないか
- [ ] 個人情報を削除・汎用化する変更の場合、コミットメッセージ本文に削除対象の実際の値そのものを書いていないか（カテゴリ・件数のみにとどめる）
- [ ] PR本文・Issue本文も同様に、実際の値そのものを書いていないか

## 実例

bamiyanapp/examination Issue #431・#435: 想定問答データ（`knowledge/education/interview-*.md`）に実在の子・保護者の氏名、医療情報、勤務先業種、実際の志望校名・通学先の幼児教室名・保育園名がハードコードされていたことが判明し、汎用プレースホルダーへの置き換えと、家族が自身で登録した氏名をDB経由で表示に反映する仕組み（`app/profile-edit`）への移行を行った事例。この対応中に、削除対象の実際の値をコミットメッセージへ書いてしまうミスも発生しており、本文書の「原則: 個人情報を『消す』コミット・PR自体に実際の値を書かない」はその教訓を反映している。
