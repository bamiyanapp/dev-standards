# Verifier

目的

成果物がGoalを満たしていることを保証する。

Verifierは以下で構成される。

1. 静的チェック
2. コードレビュー
3. Goal確認

失敗した場合は修正後、
Verifier全体を再実行する。

Verifierが成功するまで

- コミット
- 完了報告

を行ってはならない。

## 静的チェック

対象パッケージすべてで

- lint
- test
- build

を実行する。

エラーがあれば修正して再実行する。

### CI/CDワークフロー自体を新規追加・変更した場合

`ci.yml`/`cd.yml`自体を新規追加・変更した場合、lint/test/buildの結果だけでは検知できない不備（実行コマンドの相違・実行ディレクトリの相違・ルート直下でのみ必要な依存の欠如等）がCI実行で初めて判明することがある。呼び出し先の`reusable-ci.yml`/`reusable-cd.yml`のソースを確認し、各ジョブが実際に実行するコマンドを特定したうえで、pushする前にローカルで一字一句再現して成功することを確認する。

特に以下はズレが生まれやすいため明示的にチェックする。

- `--coverage`系オプションの有無（`npm test`とCIの実行コマンドが異なる場合がある）
- 実行ディレクトリ（リポジトリルート直下 vs 各パッケージディレクトリ）
- ルート直下でのみ必要になる依存関係（commitlint関連等）

### `docs/`配下に参照側プロダクトでの個別適用を要する規約を新設・変更する場合

UIコンポーネント規約等、`docs/`配下にドキュメント化するだけでは各プロダクトへ自動的に反映されず、プロダクト側の個別対応が別途必要な規約を新設・変更する場合、そのドキュメント化だけで完了とせず、以下を行う。

- `docs/consumer-repositories.md`に列挙された**全リポジトリ**を対象に、規約ドキュメント自身へ「適用状況」セクションを設ける。このセッションがアクセスできるリポジトリだけを書かない（一部のリポジトリしかアクセスできないセッションが大半のため、書いたリポジトリしか記録しないと必ず漏れが生じる）
- アクセスできず適用状況を確認できないリポジトリは「未確認」として明記する（省略しない）。確認・対応は、そのリポジトリにアクセス可能な別セッション・人間が本ドキュメントを見て後追いで行う運用とする
- 自分のセッションがアクセスできるリポジトリについては、その場で適用まで行うか、適用状況セクションへ具体的な追跡Issue番号を記載する

「各プロダクトへの適用は別途対応する」と書いただけで終わらせると、実際に追跡Issueが起票されないまま放置されがちなため、ドキュメント自体に適用状況を持たせて可視化する。

## コードレビュー

code-review Skillを使用する。

レビュー観点

- 要件
- バグ
- テスト
- 可読性
- 将来の保守性
- セキュリティ
- ドキュメント整合性
- 肥大化

## Goal確認

以下を満たすこと。

- 要件達成
- lint成功
- test成功
- build成功
- code-review成功
- 人間による手動確認手順を要求する場合、スマホのみで実行可能か（CLAUDE.md「開発環境の制約（スマホオンリー）」参照）
- コミット作成可能
